> Lead（K3）负责的外部调研。两份第三方盲审报告见 docs/review-A.md、docs/review-B.md。
> 调研问题：业界"贵模型指挥、便宜模型干活"现在做到哪了，我们差什么。

## 1. Anthropic 官方 Coordinator pattern（2026-07 cookbook）

来源：[Claude Cookbook: Coordinator pattern](https://platform.claude.com/cookbook/managed-agents-cma-plan-big-execute-small)

要点：
- **frontier coordinator 不碰原始数据**：便宜 worker 在自己独立上下文里读海量网页，回给 coordinator 的只有蒸馏后的 findings。实测 **84-98% 的 input token 记在 worker 价**。
- **对照组方法论**：同等问题用"同验证标准"的单强模型跑，比真实账单——严谨的 cost 对照才有说服力。
- **server 级 budget 护栏**：session 带 `budget` 硬顶，fan-out 失控时暂停而不是跑飞账单。
- **per-thread usage.list_cost**：每线程 token 成本 server 端计价，成本归属不用自己猜。

对我们的启发：
- 「Lead 不读原文」我们只做到了一半——回执全文（含命令原样输出）仍进 Lead 上下文。业界做法是 worker 回「蒸馏 findings」，原文留在 worker 侧。
- **缺 budget 硬顶**：我们的 handoff.md 只有人工约定，没有代码级熔断。
- **缺成本归属**：dsh 子代理面板有 token 数但没有美元计价；账单全靠用户自己算。

## 2. 上游同族竞品：thx0701/osslab-manager（2026-09-27 发布，10 star）

来源：[osslab-manager](https://github.com/thx0701/osslab-manager)（Claude/ZCode/Codex/Cursor 通用 skill + Relay CLI）

与我们几乎同题：强模型当技术长拆单验收、DeepSeek Flash 施工、异族（Grok/GLM）审查、逐张验收提交。**这是独立平行实现，可作直接对照。**

它有而我们没有的（值得吸收）：
1. **持久执行底座 Relay（osrelay）**：SQLite 记每张单、每次 attempt、证据指纹。**工人比技术长活得久**——session 断了用 `osrelay context` 接手，不靠记忆。我们的 _tickets/ 是纯文件，断会话恢复靠 Lead 重读文件。
2. **证据指纹**：`verify`/`review` 结果绑 git 版本 + 文件哈希；accept 机械核对"每条验收命令最新一次都成功、对应当前 HEAD、证据文件没被换掉"。**比我们"Lead 重跑验收命令"更硬**——防的是回执与代码版本错位。
3. **三段式 session（规格段→施工段→验收段）**：每段结束写约 2KB 交接文件，下一段只读交接开工。对症"session 越往后判断越糊"。
4. **工单链（chain）+ 独立 worktree**：依赖单共用一棵 worktree 串行，互不依赖的链并行。
5. **--resume 门禁**：接续记忆有条件（工单冻结一致、HEAD 一致、上份回执风险为"无"等），拒了就从零派。"记忆不是证据"。
6. **中断收尸**：backup-worktree.sh + SHA256SUMS 的备份/还原协议。
7. **goal 三要素**：边界/成功信号/权威契约——比我们"写两张派一张"更结构化。

它没有而我们有的：
- **dsh 原生按次换模型**（subagent provider/model 参数）——它靠外部 CLI（pi）
- **物理只读审查实例**（subagent_readonly）——它靠提示词约定
- **pick_route 硬约束**（高峰锁/视觉/输出上限/异族拒审）+ **doctor 自检** + **角色表热更新**
- **skill 自动安装**、小白三步

## 3. Context engineering 理念（2026 社区共识）

来源：[merve/hermes-agent context-budget-discipline](https://huggingface.co/buckets/merve/hermes-agent/tree/skills/software-development/subagent-driven-development/references/context-budget-discipline.md)（源自 [gsd-build/get-shit-done](https://github.com/gsd-build/get-shit-done)，MIT）

要点（对我们最有用的四条）：
1. **frontmatter-only 读取**：orchestrator 读子代理产物只读结论头，不读全文——"3000 行调试日志读 summary 段，不读日志"。我们回执模板没有 frontmatter 结论头。
2. **四档上下文降级**（PEAK/GOOD/DEGRADING/POOR，按 30/50/70% 阈值）：越到后面越省，70%+ 立即 checkpoint。我们只有"30 万 token 另开单"一条粗规则。
3. **前置 must-have 确认**：派单时就写明"必须确认的事实清单"，子代理回答里逐一断言——模糊摘要不算证据。
4. **早期预警信号**：静默半完成、措辞变虚、跳步骤 = 上下文压力的前兆。

## 4. 其他动态

- **GitHub HydraFusion**（研究预览）：多模型路由（规划/执行/验证分派不同模型），官方评测成本降 67%、质量多数持平仅一项落后。验证了"按阶段分派模型"方向，也验证了质量风险真实存在（所以我们的异族审查是对的）。
- **Claude Code subagent 成本翻车案例**（issue #97784）：子代理重读文件吃掉 47-91 万 token——"重复 prefill"是行业通病，佐证我们的 fork/subagent 分工纪律有必要量化。

## 5. 差距结论（供 v0.3 规划引用）

| 能力 | 业界标杆 | 我们 | 差距 |
|---|---|---|---|
| Lead 不碰原文 | coordinator 只收蒸馏 findings（84-98% token 在 worker 侧） | 回执全文进 Lead | **大** |
| 成本护栏 | server budget 硬顶 + list_cost 计价 | 无（人工约定） | **大** |
| 断会话恢复 | Relay + 证据指纹 + context 接手 | 文件契约 + Lead 重读 | 中 |
| 上下文预算管理 | 四档降级 + must-have 确认 | 一条 30 万粗规则 | 中 |
| 验收硬绑定 | verify/review 绑 HEAD + 文件哈希 | Lead 重跑命令 | 中 |
| 按次换模型 + 物理只读 | 无先例（外部 CLI 方案做不到） | ✅ 我们独有 | 领先 |
| 角色表热更新 + doctor | 无先例 | ✅ 我们独有 | 领先 |

## 6. 补充调研：断会话恢复与验证硬绑定（osslab Relay 细节，2026-10-01 补）

osslab-manager 的 Relay 文档（docs/relay.md / recovery.md / handoff.md / waiting.md）可提炼为三条对我们直接可用的设计：

1. **证据指纹绑定**：`accept` 前机械核对——(a) 每条验收命令的最新一次执行都成功；(b) 最新审查成功（低阶单可注明理由豁免）；(c) 都对应当前 git HEAD；(d) 证据文件哈希没被换掉。改了代码就全部重跑。→ 我们的 pick_route doctor 可扩展一个 `verify` 子命令做同样的机械核对。
2. **交接文件规范**：每段结束写 ~2KB 交接（目标原话/不做清单/下一段/HEAD/下一步动作/未定决定/证据路径），下一段只读交接开工，不重跑盘点。→ 我们的 handoff.md 目前只用于无人托管，可推广为常规换会话协议。
3. **中断收尸协议**：backup-worktree.sh + SHA256SUMS；恢复前独立 checkout 验证；不做整树 reset/clean。→ 我们的 SKILL.md 只写了"会话中断按 queue.md 续"，缺工单中途断的收尸协议。

注意：Relay 是独立 CLI（SQLite），与我们"dsh 原生、不重造任务板"的定位冲突。v0.3 不引入 CLI，但**验证硬绑定**（#1）可用 pick_route/pick_route doctor 的纯文件实现：回执里记录 `HEAD + 验收命令输出哈希`，doctor 的 accept-check 模式核对。纯文件、零依赖，保留我们特色。
