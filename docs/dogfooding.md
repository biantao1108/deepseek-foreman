# Dogfooding：用自己的工单流程跑出来的第一批实证

**本项目就是用这套系统（`skill/deepseek-foreman/`）迭代完成的**：2026-10-01 凌晨到上午，本项目用自己的工单托管流程跑完了发布冲刺的第一整轮：派单 → 施工 → 异族只读审查 → Lead 逐条核实 → 修复回单，M1（开源文档面）与 M2（只读实例 + skill 自动安装 + 自检加固）两个里程碑全部闭环。这份记录是公开版，绝对路径与私有路由名都已脱敏，路由一律写成 `vendorX/modelY` 占位。

本文档占位映射（vendorX/modelY）仅本文档内有效：`vendorB/modelB` = 第一批施工方，`vendorD/modelD` = M2 起接活的施工方（中途换过一家），`vendorA/modelA` = 异族审查方。

## 流程

每张工单都走同一套：

1. **派单**：Lead 把活写成工单落到 `_tickets/doing/`，指定施工路由、推理档位、边界，以及可直接复制的验收命令。
2. **施工**：工人模型只按工单改文件；回执写回 `_receipts/`，每条验收都贴真实命令和原样输出。
3. **异族审查**：换一家厂商的模型做只读审查，自己独立重跑验收命令，按高 / 中 / 低分级给发现。
4. **逐条核实**：Lead 对每条发现做「成立 / 不成立」裁决并写清依据；成立的要么并进后续单，要么当场闭环。

## 这条流水线实际抓到了什么

- **出厂示例的 `~` 展开坑**：`rolesFile` 不展开 `~`，注释里的示例会让用户在 cwd 下建出一个字面名为 `~` 的目录。这是纯代码审查才能从示例反推出来的用户级坑。
- **TOCTOU 方向错误**：先读内容后 stat、把新 mtime 配旧内容记下来，会从此永久漏掉一次热更新。只有把「读」与「stat」的先后当成契约来审，才会注意到。
- **回退验证（mutation testing）**：T102b 修完 5 条后，工人逐条把修复临时改回旧写法、确认对应新自检真的失败、再改回来。这证明新断言不是「永远为真」的摆设。
- **两起离线全绿、live 才炸的事故**：
  - **T205（preset scope）**：T204 给 bundle 层 standing 挂载的只读实例加了 `modelSelectionSettings: true`，离线 109 项自检全绿，装进 dsh 后 `subagent_readonly` 整个消失——运行版源码里这个开关必须落在 preset scope 内，bundle 层挂载没有 preset scope → 直接 throw、实例加载失败。回退后把断言改成反向（必须不存在），再被加回来就红。
  - **T207（全局工具表）**：`toolFilter.deny` 名单里写了子组合全局工具表中并不存在的 `subagent`，`restrict()` 直接报 `names unknown global tool`。YAML 解析和单测都发现不了，`subagent_readonly` 派单那一刻才炸；删掉后 deny 恰好剩 3 个委派/编排工具，绕过由 `maxDepth: 1` 兜底。
  - 共同教训：**离线单测只证明配置写对了，证明不了 dsh 会收下它**——bundle 层的每条改动都得装进 dsh 活跑一次。
- **`subagent_readonly` 是测出来的，不是写出来的**：live 实测确认只读子会话运行时只剩 `read` / `grep` / `glob`，`subagent_fork` / `workflow` 因 deny 从提示里消失，残留的 `subagent` 被 `maxDepth: 1` 挡住——委派绕过在真实会话里被拦死。
- **自检数长在真实缺陷上**：这条线跑下来自检从 20 → 42 → 62 → 107 → 110（M1 收在 62，M2 收在 107，T207 之后 110），每次新增都对应一个被抓到的具体问题。
- **token 开销实证**（来源：dsh 子代理面板截图；口径＝该次施工会话累计 token）：施工类工单 33 万–59 万 token/单，验证类调用 0.6 万–1.6 万 token/次。施工 token 全部发生在便宜模型上，Lead 上下文只放工单/回执/审查意见、不读代码——这就是省钱机制；未做严格 A/B 对照实验，不给百分比承诺，读者可在 dsh 子代理面板自行核对每条开销。
