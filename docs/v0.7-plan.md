# v0.7.0 方案：五阶段 token 计数 + 大版本迭代

> 日期：2026-10-04 | 需求包：`_tickets/req-2026-10-04-五阶段计数与大版本迭代.md`
> 结论：**可做，两张单落完**。需求包有三处需更正（见下），其中一处是它没发现的真 bug。

## 一、需求包评审（结论先行）

### 采纳的
- 四要素齐全；边界（不兼容 / 不设预算 / 不发 npm / 不动 f1）全部接受。
- 秘书推断 #1（role key `lead` → `foreman`）：**采纳并升级为已定决策**。大版本已允许破坏性改动，文档与配置两套叫法是真实口径债；本机 `~/.dsh/foreman.roles.yml` 同步改两行（`lead`→`foreman`、`lead-backup`→`foreman-backup`），成功信号 5 本就预设了这一步。
- 秘书推断 #3（不发 npm）：**采纳**，与边界一致。

### 更正的
- **秘书推断 #2 半对，侦察后更正**：
  - 对：`cost_session=recent` 的 `CostRow` 只有 `{session, totalTokens, inputTokens, outputTokens}`，确实无模型维度；dsh 0.2.0-rc.2 底层 token-meter 的 `tokenUsage` projection 也只有 4 个桶的 totals，无按模型分解。
  - 错：**五阶段归因不靠模型维度，靠会话身份**——每个阶段是独立会话，foreman 派单时就知道「会话 X = worker 阶段」。模型名可从会话事件日志（`model/selection` / `request/header` 事件带 provider/model）在插件侧补出，**不需要扩展 dsh**。所以方案是：cost 模式补模型维度（让 recent 行自描述），但不是五阶段计数的前置条件。
- **需求包漏了一个真 bug（侦察新发现）**：`src/index.ts` 的 `readCost` 读 `totals.inputTokens`，但 dsh 0.2.0-rc.2 实际存的键是 `uncachedInputTokens`（证据：`dsh-token-meter/lib/types/usage-projection.js` 的 `zeroBuckets()`/`bucketsFrom()`）→ **live 下 inputTokens 恒为 0**，input/output 分解是假的（totalTokens 不受影响，因为是全键求和）。`test/smoke.mjs` 的 mock 用了同样的错键，所以全绿也没抓到。**不修这个，「五阶段计数」就是空转**。

## 二、架构取舍

1. **阶段归因 = 会话身份，不是模型维度**。台账五列（session/foreman/worker/reviewer/report）由记账方（Lead/秘书）在派单与收单时按「这个子会话是哪张单的哪个阶段」填，cost 只负责给 token 真数。
2. **cost 模式做小增强，不做大改**：修键名 bug；`CostRow` 补 `cacheReadTokens`/`cacheWriteTokens`（recent 现在丢 cache 桶，单会话模式却有——同族不一致）；recent 行附 `model`（从 session 事件日志读，读不到就省略字段，**不编**）。
3. **role key 改名是数据层改动，不是代码层改动**：`pick_route` 的 role 是角色表数据驱动的，代码里只有工具描述字符串提到 `lead`（src/index.ts:654）。改名风险集中在「全仓文档/配置扫尾」，不在逻辑。
4. **不做向后兼容**：不保留旧键名回退（`inputTokens` 直接换成 `uncachedInputTokens`），不留 `lead` 别名。
